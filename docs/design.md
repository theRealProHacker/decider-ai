## Problem Statement

Teams that route incoming messages (support tickets, client mail) with an LLM call send private text to a general LLM vendor and have no measured accuracy. Teams that want a small private model instead must assemble labels, training, evaluation, serving and rollback themselves. The product hypothesis: a self-hostable endpoint that serves typed decisions, captures operator corrections, and retrains or deploys a model only when the user explicitly asks; evaluation results inform that choice but never act on their own.

## Recommended Approach

### Phase 0 — Eval gate (1–3 weeks, bounded by consent and labelling throughput; engineering itself is days)

Text form everywhere: Pilot's gateway pseudonymizes before any model call (Pilot rule 3). Training, eval and serving all use the same pseudonymized text, so there is no train/serve skew. Privacy claim vs Gemini restated: pseudonymization stays; what changes is that even pseudonymized text no longer leaves the firm's server or reaches a third-party provider.

In Pilot (separate repo, separate PR):
1. Confirmation queue (backlog item "Posteingang-Queue mit Bestätigung"): per mail, store the model's prediction, the lawyer's one-click confirm/correct, the decision source (rule or model), and a `label_mode` flag (`assisted` = prediction shown, `blind` = not shown).
(Pilot detail removed)
3. Export labels as JSONL in the decider-ai record format (source plan §6.1: `external_id`, `input.text`, `labels`, `group_id`, `provenance` incl. `label_mode`).

In decider-ai:
4. Eval script comparing (a) rules only, (b) rules + Gemini Flash Lite, (c) rules + Laya fine-tuned on CPU. Group-aware split (same thread stays in one split). Report per-label precision/recall, confusion matrix, CPU latency.
5. Label budget. First measure the rule-matched share from one week of queue provenance. Blind labelling continues until the test set holds ≥100 rule-unmatched mails with ≥15 per action class; ~250 blind labels is the starting estimate, not a cap. Until the gate decision is recorded, every blind label goes to the test set (including the branch-3 growth toward 400). Training uses assisted labels from the live queue only. Blind labels may enter training only after the gate decision. Rule-decided mails are excluded from both training and test (the model never sees them in production).
6. Action gate metric: macro-F1 on the action label (new / follow-up / ignore), on the blind rule-unmatched test set. Uncertainty: **paired bootstrap on the difference** Δ = (c) − (b), 2,000 resamples of test mails; within each resample, (c) is the mean over 5 seeds. Report Δ and its 95% CI.
7. Urgency gate (separate): mean absolute error on the same test set, paired bootstrap on ΔMAE = MAE(c) − MAE(b). Urgency moves to the local model only if the upper CI bound of ΔMAE ≤ 0.3; otherwise Pilot keeps urgency on Gemini.
8. Learning curve: (c) macro-F1 at 50 / 100 / all available training labels. "Rising" means macro-F1 at "all" exceeds macro-F1 at 50 by more than twice the seed standard deviation at "all".

Action gate decision, evaluated in this order (first match wins):
1. Upper CI bound of Δ < −0.05 → (b) wins. Product value is correction capture + audit, not fine-tuning. Re-scope before Phase 1 (e.g. endpoint fronting a local LLM with feedback-as-few-shot). No "fine-tune" tutorial.
2. Lower CI bound of Δ ≥ −0.05 (non-inferior within 5 points) → build Phase 1. Headline states the measured Δ as a number (e.g. "within N points of Gemini, with no text leaving the server"). Add "improves with corrections" only if the curve is rising.
3. Otherwise (CI spans the margin) → label more. Re-run the gate each time the test set grows by 100 mails. At 400 test mails, decide on the point estimate: Δ ≥ −0.05 → branch 2, else branch 1.

### Phase 1 — Open-source launch

Single container, `docker run`.

**Tasks and schema.** A `tasks.yaml` on the mounted volume defines one or more tasks (name, label set, single- or multi-class, max input length). Each task also carries a question and a one-line description per label. Laya is a question-plus-options decision model, so a task is encoded as question + label options, not as a new classification head. One container serves several tasks; each task gets its own fine-tuned checkpoint in that same format. Pilot uses two: `mail_action` and `urgency`. Changing a task's label set creates a new task version and requires retraining.

**Cold start.** The image bundles the base checkpoint. Before any training, `/v1/decisions` serves the base model's zero-shot answer to the task's question and options, labelled `model_version: base`. Phase 0 measures base zero-shot quality as a fourth baseline, (d). If the chosen checkpoint cannot answer zero-shot usefully (macro-F1 not above the majority-class baseline), the image ships with zero-shot disabled: `/v1/decisions` returns `503 MODEL_NOT_TRAINED` until a first model is active. First-model rule: a trained candidate never activates itself. The 503 ends only when the user explicitly calls `/v1/models/{version}/activate`. The candidate's report compares it against the majority-class baseline so that choice is informed. `/health/ready` reports per task `base`, `trained` or `not_trained`. `POST /v1/examples:batch` imports labelled JSONL (e.g. the Phase 0 export) so a user can train before going live.

**API.**
- `POST /v1/decisions` — `{task, text, external_id?}` → predictions + scores, `model_version`, `request_id`. Over-length input (limit per task in `tasks.yaml`, exposed in `/health/ready`) returns `413` with code `INPUT_TOO_LONG`; never truncated. Pilot's fallback on any error: route the mail to manual review, as today when AI is disabled.
- `POST /v1/feedback` — `{request_id, labels}` → stored as a confirmed example.
- `POST /v1/examples:batch` — labelled JSONL import.
- `DELETE /v1/examples/{external_id}` — erases stored text and labels for that ID (erasure requests).
- `POST /v1/retrain` — `{task}` → `202` + `job_id`. One job at a time across the container (second request → `409`). `GET /v1/jobs/{id}` → status, progress, eval result.
- `GET /v1/models?task=` — versions with eval metrics and which is active.
- `POST /v1/models/{version}/activate` — rollback/roll-forward. Labels and pending feedback are unaffected; the frozen test split is unchanged.
- `GET /health/live`, `GET /health/ready`.

**Text storage.** Decision inputs are stored in SQLite (not logs) so feedback can reference them. Unconfirmed decision text is purged after a configurable retention (default 30 days); confirmed examples are kept until deleted. No message text in logs, ever.

**Retrain and activation.** Rule (founder, 2026-10-08): decider-ai retrains or deploys only on explicit user request. No scheduled, threshold-triggered or automatic retraining; no automatic activation. This applies to the API, the n8n node and any coding agent following the docs.
- Minimum 50 confirmed examples per task before retrain is allowed.
- The test split is a fixed 100 examples, group-aware, frozen once ≥150 confirmed examples exist (leaving ≥50 for training) with ≥10 per label in the split. Any confirmed example is test-eligible. Split examples never enter training. Batch-imported examples marked `label_mode: blind` are preferred for the split; otherwise it is drawn from all confirmed examples. The split is refreshed only by explicit `POST /v1/retrain {task, refresh_split: true}`, which re-evaluates the active model on the new split too.
- Recommendation, not promotion: each finished retrain job reports a paired bootstrap of macro-F1 (candidate − active) on the frozen split, with a verdict of `recommended` (lower 95% CI bound > 0), `not_recommended`, or `unverified` (no split yet). The active model never changes until the user calls `activate`. Activating a `not_recommended` or `unverified` candidate succeeds but returns a warning.
- Before the split exists (fewer than 150 confirmed examples), retrain still runs, but the candidate is stored as `unverified`. It can only be activated manually via `/v1/models/{version}/activate`, and the response carries a warning that it has no reliable evaluation.
- Training runs in a background worker thread at `nice` priority with a configurable thread cap (default: half the CPUs). Decisions keep serving from the active model during training. Publication is an atomic swap: load candidate, verify a smoke prediction, flip the active pointer in SQLite, then release the old model.

**Network and auth.** The process binds `0.0.0.0` inside the container. Docs publish only to host loopback (`-p 127.0.0.1:8080:8080`). The API key comes from `DECIDER_API_KEY`; if unset, one is generated on first start, printed once and stored on the volume.

**Pilot integration.** Provider `local` behind the existing `LLMClient` interface, called through the gateway with the same pseudonymized text as Phase 0. Pilot calls `/v1/decisions` only for mails its deterministic rules did not decide. Pilot switches each task to `local` only if that task passed its own Phase 0 gate: action via the action gate, urgency via the urgency gate. A task that failed stays on Gemini.

## Success Criteria

- Phase 0: a three-way eval report meeting the gate minimums (≥100 blind rule-unmatched test mails, ≥15 per action class), with confidence intervals, learning curve and stated sample sizes; gate decision recorded.
- Phase 1 release test, on a clean machine with `docker run` and a `tasks.yaml`:
  - Cold start: with zero-shot enabled, a decision returns `model_version: base`; with it disabled, `503 MODEL_NOT_TRAINED`.
  - Below 150 examples: import labels, send feedback, run a retrain job and poll it; the candidate is `unverified`; activate it manually; decisions now serve it.
  - At ≥150 examples: retrain; the job reports `recommended` or `not_recommended`; the active model is unchanged until an explicit `activate`.
  - Activate the previous version via `/v1/models/{version}/activate`, delete an example, restart without losing labels or the active version.
- Validation (30 days after launch): ≥3 inbound conversations from people with a real routing problem who will share data or pay for installation/training. Stars, pulls and visits do not count.
