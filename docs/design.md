## Problem Statement

Teams route incoming messages (support tickets, inbound mail) into a fixed set of queues with an LLM call. They send private text to a vendor, pay per call, wait on a network round trip, and have no measured accuracy. Teams that want a small private model instead must assemble labels, training, evaluation, serving and rollback themselves. Hypothesis: one container that replaces that LLM call, learns from the corrections operators already make, and retrains or deploys a model only when the user explicitly asks.

## Demand Evidence

- None yet. No named user (founder, 2026-10-08: "Nobody named yet"). Pilot is no longer the case study: its mail call is not a fixed-label decision.
- The launch itself is the demand test (Premise 1).

## Status Quo

- One LLM API call returning JSON, or helpdesk built-in triage (Zendesk, Freshdesk, Intercom). Znuny-LLM offers self-hosted classification via Ollama with agent-confirmed few-shot examples.
- Landscape (search, 2026-10-08): fine-tuned small models usually beat zero-shot LLMs on fixed-label ticket classification once labels exist (typical vendor ranges: 0.80–0.87 F1 zero-shot vs 0.88–0.94 fine-tuned); received wisdom says 1,000–5,000 labels per category; hybrid routing (confident classifier, uncertain cases escalated) is the common pattern; model self-confidence is uncalibrated; small-model routing posts are appearing. decider-ai's testable bet: a question-plus-options model gets useful with ~50–250 corrections.

## Target User & Narrowest Wedge

- Target: developers and operators who classify inbound messages into fixed queues with an LLM call today. No named person yet.
- Wedge: a drop-in container for that call, with correction capture, explicit retrain/activate and rollback, measured on public data.

## Constraints

- Solo founder.
- Model licences: commercial use only (Laya Apache-2.0 per source plan; `openjev/openjev` is non-commercial — do not use). Benchmark datasets likewise (Tobi-Bueck customer-support-tickets rejected as CC BY-NC 4.0).
- The product never calls an LLM. An LLM appears only as an offline baseline in the eval script, on public data.
- Founder rule: no automatic retrain or activation, ever (decision 83b5e76c).

## Premises

1. decider-ai launches with no named customer. The launch is the demand test; validation stays ≥3 inbound conversations within 30 days from people with a real routing problem who will share data or pay for setup. Stars, pulls and visits do not count.
2. Pilot leaves the launch: no case study, no gate, no Phase 1 integration.
3. The Phase 0 gate runs on 2–3 public routing datasets (resolved: MASSIVE 1.1 `de-DE` at scenario level and CLINC150 `oos_plus` at domain level; see `docs/research/public-benchmark-datasets.md`). Systems: (c) fine-tuned Laya, (d) base zero-shot, majority class, TF-IDF + logistic regression, and (b) an LLM baseline the eval script runs offline on public data only.
4. The gate is cost-benefit (founder: "If gemini is cheaper, faster AND better, then we have a problem"). Re-scope before launch only if, on every benchmark dataset, the LLM baseline dominates (c) on all three axes at once: lower cost per 1,000 decisions, lower p95 latency, and higher macro-F1 at 250 training labels with the 95% CI on the difference above zero. Otherwise launch, and the headline states the trade-off measured, e.g. "N points behind at 250 labels, X× cheaper, p95 Y ms, no text leaves the server".
5. Phase 1 scope stays as designed, including the n8n node. `decide` returns scores; the caller owns the fallback for low-confidence cases. decider-ai adds no LLM fallback.

## Recommended Approach

Two tracks built at the same time. The gate decides the launch headline and whether to re-scope; it does not gate starting the product track.

### Track 1 — Eval and model (Phase 0)

1. `LayaBackend` (built fresh on the Apache-2.0 `laya` SDK; https://github.com/tehtommeh/laya-finetuning is reference reading only) and `decider-eval`.
2. `decider-eval` reads labelled JSONL in the decider-ai record format with any number of named, optional external prediction systems (e.g. `majority`, `tfidf_lr`, `llm`). (c) is the fine-tune over 5 seeds via `Backend`; (d) is zero-shot via `Backend`.
3. Per dataset: the official test partition is the blind test set (`label_mode: blind`); `group_id` = `external_id` where there are no threads. Learning curve for (c) at 50 / 100 / 250 / all training labels.
4. Report per system: macro-F1 with paired-bootstrap CI on the difference vs (c) (2,000 resamples, seeds averaged inside each resample); p95 latency per decision; cost per 1,000 decisions. LLM: provider list price at run date. Local: inference CPU-hours on a stated reference machine plus training cost, with one retrain at 250 labels amortised over a reference volume of 10,000 decisions per month for 3 months (30,000 decisions); training CPU-hours are also reported as their own line so readers can rescale to their volume. Aggregate numbers only.
5. Gate (Premise 4, one rule): re-scope before launch if, on every dataset, (b) has lower cost per 1,000 decisions, lower p95 latency, and higher macro-F1 than (c) at 250 training labels with the 95% CI on the difference above zero. Otherwise the headline states the measured trade-off. If Laya fails its licence or CPU checks (map ticket "Laya checkpoint facts"), Track 1 stops and the backend choice returns to the founder; a SetFit-style small encoder behind the same `Backend` port is the named fallback candidate.

### Track 2 — Product (Phase 1)

Single container, `docker run`. Built on `FakeBackend` until `LayaBackend` lands (module design: `docs/architecture.md`).

**Tasks and schema.** A `tasks.yaml` on the mounted volume defines one or more tasks (name, label set, max input length, `zero_shot: true|false`). Phase 1 is single-label: every example and decision carries exactly one label from the task's set (any number of classes; multi-label is out of Phase 1). The `labels` field in feedback and import holds exactly one label. Each task also carries a question and a one-line description per label. Laya is a question-plus-options decision model, so a task is encoded as question + label options, not as a new classification head. One container serves several tasks; each task gets its own fine-tuned checkpoint in that same format. Changing a task's label set creates a new task version and requires retraining. Clients keep addressing the task by name. Until a model for the new version is activated, the task serves its cold-start behaviour (zero-shot if `zero_shot: true`, else 503). Confirmed examples whose label is still in the new set carry over; the rest are kept but excluded. The frozen split resets with the version.

**Cold start.** The image bundles the base checkpoint. Before any training, a task with `zero_shot: true` serves the base model's zero-shot answer to the task's question and options, labelled `model_version: base`. Phase 0 measures base zero-shot quality as (d). Zero-shot is a per-task `zero_shot` flag in `tasks.yaml`, default `false`. With it off, `/v1/decisions` returns `503 MODEL_NOT_TRAINED` until a first model is active. Whether the default flips to `true` depends on the usefulness threshold for (d), an open question. First-model rule: a trained candidate never activates itself. The 503 ends only when the user explicitly calls `/v1/models/{version}/activate`. `/health/ready` reports per task `base`, `trained` or `not_trained`. `POST /v1/examples:batch` imports labelled JSONL so a user can train before going live.

**API.**
- `POST /v1/decisions` — `{task, text, external_id?}` → predictions + scores, `model_version`, `request_id`. Over-length input (limit per task in `tasks.yaml`, exposed in `/health/ready`) returns `413` with code `INPUT_TOO_LONG`; never truncated.
- `POST /v1/feedback` — `{request_id, labels}` → stored as a confirmed example. Feedback must arrive within the retention window; after the text is purged it returns `410` with code `REQUEST_EXPIRED`; an unknown request returns `404`.
- `POST /v1/examples:batch` — labelled JSONL import.
- `DELETE /v1/examples/{external_id}` — erases stored text and labels for that ID and removes it from the frozen split. It does not retrain: the response lists the model versions trained on that example, and the docs say plainly that weights derived from deleted data persist until the user retrains and activates. Records without an `external_id` cannot be deleted by this endpoint (deletion by `request_id` and the checkpoint policy: map ticket "Data lifecycle and erasure").
- `POST /v1/retrain` — `{task}` → `202` + `job_id`. One job at a time across the container (second request → `409`). `GET /v1/jobs/{id}` → status, progress, eval result.
- `GET /v1/models?task=` — versions with eval metrics and which is active.
- `POST /v1/models/{version}/activate` — rollback/roll-forward. Labels and pending feedback are unaffected; the frozen test split is unchanged.
- `GET /health/live`, `GET /health/ready`.

**Text storage.** Decision inputs are stored in SQLite (not logs) so feedback can reference them. Unconfirmed decision text is purged after a configurable retention (default 30 days); confirmed examples are kept until deleted. No message text in logs, ever.

**Retrain and activation.** Rule (founder, 2026-10-08): decider-ai retrains or deploys only on explicit user request. No scheduled, threshold-triggered or automatic retraining; no automatic activation. This applies to the API, the n8n node and any coding agent following the docs.
- Minimum 50 confirmed examples per task before retrain is allowed.
- The test split is a fixed 100 examples, group-aware, frozen once ≥150 confirmed examples exist (leaving ≥50 for training) with ≥10 per label in the split. Any confirmed example is test-eligible. Split examples never enter training. When the per-label minimum cannot be met (a rare label, or more than 10 labels), the split does not freeze, candidates stay `unverified`, and `/health/ready` names the blocking labels (interim default; map ticket "Rare-label split fallback" decides the lasting rule). Batch-imported examples marked `label_mode: blind` are preferred for the split; otherwise it is drawn from all confirmed examples. The split is refreshed only by explicit `POST /v1/retrain {task, refresh_split: true}`, which re-evaluates the active model on the new split too.
- Recommendation, not promotion: each finished retrain job reports a paired bootstrap of macro-F1 (candidate − active) on the frozen split, with a verdict of `recommended` (lower 95% CI bound > 0), `not_recommended`, or `unverified` (no split yet), and the CI shown next to the verdict. With `zero_shot: true` and no trained model active, `base` counts as the active model for this comparison. With no model active at all, the verdict is `unverified` (interim default; map ticket "First-model verdict" may set a baseline comparison). The active model never changes until the user calls `activate`. Activating a `not_recommended` or `unverified` candidate succeeds but returns a warning.
- Before the split exists (fewer than 150 confirmed examples), retrain still runs, but the candidate is stored as `unverified`. It can only be activated manually via `/v1/models/{version}/activate`, and the response carries a warning that it has no reliable evaluation.
- Training runs in a background worker thread at `nice` priority with a configurable thread cap (default: half the CPUs). Decisions keep serving from the active model during training. Publication is an atomic swap: load candidate, verify a smoke prediction, flip the active pointer in SQLite, then release the old model.

**Network and auth.** The process binds `0.0.0.0` inside the container. Docs publish only to host loopback (`-p 127.0.0.1:8080:8080`). The API key comes from `DECIDER_API_KEY`; if unset, one is generated on first start, printed once and stored on the volume.

**n8n community node** (founder): operations "Decide" and "Send feedback" against the endpoint, so n8n users get correction capture without custom HTTP wiring. Planned outside the engineering map.

**Tutorial.** The public-benchmark results from Track 1, headline set by the gate. Examples use the public datasets and the synthetic German dataset in the repo.

Deliberately deferred (gstack-shortcut, decision 18271c16 (supersedes 6ef66611)): web UI, Postgres, separate trainer service, GPU profile, CLI, AGENTS.md, multi-tenant schema, ONNX/INT8. Ceiling: single process, single tenant. Upgrade when a second named customer exists or concurrent tenants are needed.

## Open Questions

Tracked as tickets on the engineering map (`issues/0001-map-decider-ai-engineering.md`) and carried over from the previous review (R3-6..R3-14):
- Which LLM is baseline (b), at which price and settings, and which reference machine prices local CPU time.
- Zero-shot as a per-task setting and its usefulness threshold (the majority baseline scores ≤0.014 macro-F1 on the chosen sets, too low a bar).
- First-model verdict: what a retrain is compared against when no model is active.
- Rare labels that never reach ≥10 in the split; data lifecycle and erasure (purged requests, deletion without `external_id`, deleted data in the split and in checkpoints); HTTP error and idempotency details; open-source licence; non-functional targets; container build.
- Laya checkpoint facts: exact checkpoint, licence revision, CPU fine-tune time and memory, input limit (decides whether larger label sets fit), and from them the per-task memory budget and maximum number of loaded tasks. Track 2 builds on `FakeBackend` and does not depend on these until `LayaBackend` lands.
- No commercially usable public set has an urgency-like ordinal label; whether the synthetic German dataset carries one.

## Success Criteria

- Phase 0: a public-benchmark report on ≥2 datasets with macro-F1 CIs, learning curve, p95 latency and cost per 1,000 decisions for every system, sample sizes stated; gate outcome recorded.
- Phase 1 release test, on a clean machine with `docker run` and a `tasks.yaml`:
  - Cold start: with zero-shot enabled, a decision returns `model_version: base`; with it disabled, `503 MODEL_NOT_TRAINED`.
  - Below 150 examples: import labels, send feedback, run a retrain job and poll it; the candidate is `unverified`; activate it manually; decisions now serve it.
  - Once the split is frozen (≥150 confirmed examples with ≥10 per label in the split; release-test data is chosen to guarantee it): retrain; the job reports `recommended` or `not_recommended`; the active model is unchanged until an explicit `activate`.
  - Activate the previous version, delete an example, restart without losing labels or the active version.
- Validation (30 days after launch): ≥3 inbound conversations from people with a real routing problem who will share data or pay for installation/training.

### R2-1 — completeness (blocking)

**Problem**

> R1-6 is only partly fixed. DELETE now states its limits plainly: it removes the example from the split, lists the affected model versions, and says weights persist. But `external_id` is optional on `/v1/decisions`, and feedback turns such a decision into a confirmed example that is 'kept until deleted'. That example now has no erasure path at all in Phase 1, so a confirmed text without an external_id can never be erased. The original remedy's 'how to delete by request_id or for records without an external_id' is deferred to a map ticket and still unmet. For a product sold on privacy, that is a correctness and privacy gap in the committed API.

**Remedy**

> Commit to a Phase 1 erasure path for every stored record. For example, add `DELETE /v1/examples/by-request/{request_id}` (or return an example ID from feedback and delete by that), or require `external_id` whenever feedback confirms an example. Leave only the checkpoint policy to the ticket.

### R2-2 — completeness (blocking)

**Problem**

> Deleting an example now removes it from the frozen split, but the split is defined as a fixed 100 examples with ≥10 per label. The document does not say what happens next. Does the split shrink, or is it topped up from confirmed examples (which may already be in training data for existing candidates)? If a label drops below 10, does the split unfreeze, so candidates turn `unverified` and `/health/ready` reports blocking labels? Are existing verdicts recomputed? This decides whether recommendations stay valid after an erasure request.

**Remedy**

> State the split's behavior after a deletion. For example: the split shrinks and stays frozen with the remaining examples, existing verdicts stand, and the per-label minimum applies only at freeze time. Or: the split is topped up only on an explicit `refresh_split`. Then say how verdicts computed on the old split are labelled.

### R2-3 — consistency (blocking)

**Problem**

> After a label-set change, the task serves cold-start until 'a model for the new version' is activated. But `POST /v1/models/{version}/activate` takes no task or task version, and the release test does 'Activate the previous version'. The document also does not say how a new task version is detected (on restart, on a tasks.yaml reload) or whether rolling back to the old task version is possible.

**Remedy**

> Define it: `activate` rejects models from a different task version with a named error (or rolling back the label set restores the old task version and its models). Also state when tasks.yaml changes are picked up and how a task version is identified in `/v1/models`.
